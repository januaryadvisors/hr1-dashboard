# Deviations, gaps and open questions

Every item is something the build could not follow literally, or something the
spec assumes that the R side does not yet produce. Nothing here was decided
unilaterally to make the code easier — each entry says what was done and why, so
it can be overruled.

---

## A. Gaps between the spec's §3 contract and what `build_scores.R` produces

The spec says `export_tool_data.R` is unwritten (§12) but treats
`vulnerability_county.csv` as the upstream shape. Reading
`rscripts/build_scores.R` in the analysis repo turns up three mismatches that
whoever writes the export needs to resolve.

### A1. No `_moe` columns exist — BLOCKING for §10

Spec §3.1 requires `d1_moe … d5_moe`, and §10 is unambiguous: *"Every estimate
ships with its MOE. In the tooltip, in the download, in the table."*

`build_scores.R` produces `d1_score`/`d1_n`/`d1_tier` and no MOE column
anywhere. The domain scores are row means of ACS-derived percentiles
(`row_mean_skip_na(...)`), so a domain MOE has to be propagated from the
component MOEs — it cannot be recovered downstream.

The dashboard reads `d*_moe`, renders it in the tooltip and the JSON download,
and shows `—` when absent. Fixture data carries synthetic MOEs so the path is
exercised. **This is a real deliverable risk, not a plumbing detail.**

### A2. `d*_tier` is a string, not an integer

Spec §3.1 says `d1_tier … d5_tier | int 1–5`. `build_scores.R` builds tiers with
`cut(..., labels = c("Q1", …, "Q5"))`, so the column holds the factor labels
`"Q1"`–`"Q5"`.

The dashboard follows the spec and expects `1`–`5`. It also never trusts the
column: `quintile()` in `src/lib/scales.ts` derives the tier from the score, so
a string tier degrades to a display gap rather than a wrong map. The export
should emit integers.

### A3. There is no `d5_*` column, confirming the §3 warning

Searched: `vulnerability_county` has `d1`–`d4` only. The Children layer has no
source, exactly as §3 warns and §12 records.

Per §12 the layer strip therefore **ships with five live entries**. The sixth
card renders as a disabled placeholder reading "No source column yet" rather
than being removed, so the gap is visible to the client instead of invisible.
Flipping `available: true` in `src/config/layers.ts` is the whole change once
`d5_*` exists. Nothing is synthesised from the statewide age bands (§3 forbids
it).

## B. Ramp parity with `build_scores.R` — resolved, with one discrepancy to settle

§13's closing instruction: *"The domain ramps in §6.4 must match
`rscripts/build_scores.R:317–325` character for character."*

Done, and verified rather than asserted. `src/lib/colorRamp.ts` is a port of R's
`grDevices::colorRampPalette`, pinned in `colorRamp.test.ts` against values
generated by real R, plus a randomised 120-case parity test
(`colorRamp.r-parity.test.ts`) that runs whenever `Rscript` is on PATH.

Two behaviours had to be reproduced exactly, both discovered by diffing against R:

1. R normalises to `[0,1]` (`col2rgb/255`), interpolates there, then multiplies
   by 255. The roundtrip's float error is load-bearing: blue interpolates to
   `195.999999999999972`, not `196`.
2. `rgb(..., maxColorValue = 255)` **truncates**, it does not round. So that
   value becomes `195`, and `198.5` becomes `198`.

Getting either wrong shifts colours by one step — precisely the
"conversation about the tool" §13 warns about.

**Discrepancy to settle with David:** the ramps are declared as
`colorRampPalette(...)(7)` — seven colours — but `bins_score` is
`c(0, 0.2, 0.4, 0.6, 0.8, 0.9, 1.0)`, which is **six** intervals. The R comment
says "expanded to 7 bins", which is off by one against its own bins vector.

The dashboard generates **six** colours, one per interval. Leaflet resamples the
7-colour vector down to 6 internally, so the review maps and the dashboard land
within a couple of RGB units of each other — but they are not bit-identical.
Changing the `(7)` to `(6)` in `build_scores.R` would make them exactly equal.

## C. `centroid` is `[lon, lat]`, not projected x/y

Spec §3.1: `centroid | [number, number] | Projected x/y for bubble placement and
infrastructure marks.`

The fixtures store **geographic** `[lon, lat]` and the client projects them with
the shared projection object.

Reason: baking projected coordinates into the export would hard-code a canvas
size into an R script, and would break the moment a panel is rendered at a
different size — the very registration §2 asks for. The app fits one projection
to the state bbox and reuses it across every panel (§2), so projecting a lon/lat
centroid is a single call and always agrees with the polygons.

Recommend amending §3.1 to `[lon, lat]`, EPSG:4326, matching §3.2's treatment of
the geometry.

## D. Infrastructure marks are one glyph per *type*, not one per *site*

Spec §6.6: *"one per listed site, jittered inside the county so co-located sites
stay countable."*

Current build draws **one glyph per present type** in a small fan at the county
centroid — so a county with three food banks shows one filled square, not three.

Reason: one-per-site with true in-polygon jitter needs point-in-polygon
rejection sampling against 254 simplified polygons, and at ~1,500 marks it
visually overwhelms the choropleth underneath at hero size. Deferred rather than
skipped.

To finish it properly: precompute jittered in-polygon positions per site in
`export_tool_data.R` (where the polygons and the registry both live) and ship
them as a point array. That keeps the browser out of the geometry business, the
same argument §9 makes for district aggregation. The count is still available —
the tooltip lists per-type site counts.

## E. Grid style uses its own viewBox

§6.4 requires thumbnails and the hero map to "register exactly". They do, in
`geo` and `density`, via one shared projection.

The `grid` cartogram deliberately does **not** register with the geographic
views — that is what a cartogram is — so it renders on its own square lattice
viewBox. Grid thumbnails register with each other and with the grid hero map.

## F. Count measure on a layer with no count basis

C-03 covers the hero map: an amber panel naming the reason, and the toggle is
**not** greyed out. Implemented as specified.

The spec does not say what the *layer-strip thumbnails* should do in that state.
Rendering them literally ("same measure as the hero map", §6.4) produced blank
grey cards — every county at radius zero, which reads as "no exposure here"
rather than "no denominator exists". Those cards now show a
"No count basis" placeholder, following C-03's logic that the reason gets named
rather than implied.

## G. Statewide figures are reconciled; county figures are synthetic

`scripts/build-fixtures.mjs` hits every published anchor in the spec exactly:

| Figure | Source | Fixture |
|---|---|---|
| Window change | §6.1 | −547,051 ✓ |
| Peak, Jan 2023 | §8 tab 1 | 3,654,101 ✓ |
| Latest, May 2026 | §8 tab 1 | 2,971,598 ✓ |
| Nov 2025 drop | §6.8 | −110,000 ✓ |
| May 2026 change | §8 tab 1 | −78,861 ✓ |
| Participation | §6.3 | 11.0% → 9.3% ✓ |
| Age bands | §6.8 | −19.1 / −16.8 / −16.6 / −10.6 / −0.2 ✓ |
| Infra coverage | §6.6 | 181 / 105 / 134 / 114 ✓ |

County monthly enrollment is apportioned by largest-remainder so county sums
reconcile to the statewide series **exactly in all 55 months** — the hero number
equals the sum of county changes, which is the property that would otherwise
break silently.

Two fixture figures land near, not on, their targets, and are cosmetic:

- `small_denominator`: **91** counties under 10,000; §3.1 says 92.
- Cumulative impact 0–4: **118 / 81 / 44 / 9 / 2**; §8 tab 3 says
  113 / 91 / 38 / 11 / 1. Domain correlations are generated to target
  (d1/d2 = −0.324 against −0.30) but rank-transforming attenuates Pearson r, so
  d1/d3 lands at 0.35 against the 0.43 target.

All of it disappears when the real export lands. Every record carries
`fixture: true`, and the app shows a standing banner while it is set.

## H. Not built yet

Deliberate, following §13's build order. Nothing here is blocked by anything above.

- **Insights tabs** (§8) — routing, chapter framing, the "what this does not
  support" line, and tab 1's monthly-change and tab 2's dumbbell charts are in.
  The remaining eleven charts are listed in-page so the gap is visible.
- **Districts** (§9) — renders from the empty state as §3.4 requires; the US
  House control is present and disabled with the blocker in its tooltip.
- **Accessibility pass** (§13 step 9) — keyboard map navigation, focus rings and
  per-county `aria-label`s are in; still owed are the text-alternative table
  behind each map and a contrast audit of every ramp's mid stop.
- **Dark mode** — out of scope for v1 (§1). Tokens are authored as custom
  properties and §12's lightened ramps are declared in `tokens.css`, unused, so
  the theme is a stylesheet change.
- **Vitest on presentational components** — §2 says not to, and we don't. Tests
  cover the scale, binning, ramp, format, density and state helpers, "where a
  silent error changes what the map claims."
